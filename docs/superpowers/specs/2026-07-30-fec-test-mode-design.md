# FEC 测试模式设计 (`--test-mode`)

日期: 2026-07-30
状态: 已确认,待实现

## 1. 目标

新增一个一次性运行的测量模式,探测链路真实丢包特征,输出**三档可选的 FEC 配置建议**(`-f` 与 `-i`),并判断该链路的丢包是否**适合用 FEC 解决**。

### 目标

- 测出链路的丢包率、丢包连长分布、突发时长
- 上下行**分别**给出建议(FEC 是分方向的:client 的 `-f` 只管上行,server 的 `-f` 只管下行)
- 给出三档候选配置,每档附预计残余丢包、冗余开销、实际占用带宽
- 判断丢包是**随机型**(FEC 适用)还是**限速/拥塞型**(FEC 无效甚至有害)
- 对比单端口与 port-range 多端口的丢包差异,量化 port-range 是否有效

### 非目标(明确排除)

- **不做自适应/闭环调参**。不通过 `--fifo` 自动改参数,只打印建议供人工采纳。
- **不做实测验证档**(即"按推荐配置真跑一遍再核对残余丢包")。评估器与探测器的设计不阻碍将来追加此功能。
- **不推荐 `--timeout` / `--mode` / `--mtu`**。这三者主要由应用流量特征与路径 MTU 决定,靠丢包探测推不出来,强行给值等于给出无依据的数字。
- **不做饱和式容量测量**。侵入性过强,且饱和产生的拥塞丢包会污染 FEC 轨迹。
- **不推荐细粒度 `-f x1:y1,x2:y2,...`**。只输出单一 `x:y`。

## 2. 用户接口

```bash
# responder(对端)
./speederv2 -s --test-mode -l0.0.0.0:4096 -k "pd" \
    [--data-port-range 15000-15015]

# prober(发起端,打印报告)
./speederv2 -c --test-mode -r107.182.185.31:4096 -k "pd" \
    [--data-port-range 15000-15015] \
    [--test-duration 30] [--test-pps 200] [--test-pkt-size 1200] \
    [--test-app-mbps 5]
```

### 新增参数

| 参数 | 默认 | 上限 | 说明 |
|---|---|---|---|
| `--test-mode` | off | — | 启用测试模式。`-c`/`-s` 继续区分角色 |
| `--test-duration` | 30 | 600 | 每个探测阶段的时长(秒) |
| `--test-pps` | 200 | 20000 | 探测发包速率 |
| `--test-pkt-size` | 1200 | 1400 | 探测包总长(含头与 MAC) |
| `--test-app-mbps` | 探测速率 | — | 你的业务净荷速率,用于把冗余比换算成绝对带宽 |
| `--test-selftest` | off | — | 隐藏开关:用合成轨迹跑评估器断言,打印 pass/fail 并以退出码反映 |

### 复用的现有参数

- `-k`:**测试模式下强制必填**(见 §9 安全)。
- `--data-port-range a-b`:给了则额外跑多端口对比阶段。**两端都要写,且必须一致**——测试模式不实现第二套 control-plane 握手来下发端口表,两边填同样参数是可接受的成本。
- `--random-drop`:见 §10,测试模式在自己的发送函数里实现同等的丢包注入。

## 3. 架构

### 代码落点

新增 `test_mode.h` / `test_mode.cpp`,自成一体。**不复用** `fec_manager` / `connection` / `packet` 那条隧道链路。`main.cpp` 中新增一个 `working_mode`(与现有 `tunnel_mode` / `tun_dev_mode` 并列),由 `--test-mode` 选中,再按 `-c`/`-s` 分派 `test_mode_prober_loop()` / `test_mode_responder_loop()`。

### 角色

- **prober(`-c`)**:全程编排者。发探测流、记录自己收到的轨迹、跑评估器、汇总并打印报告。
- **responder(`-s`)**:听指令方。绑定 `-l` 端口(以及 `--data-port-range` 的 N 个端口),按 prober 指令收/发探测流,记录自己收到的轨迹,本地评估后回传结果。

### 探测是单向的(无 echo)

接收方靠**序号空洞**统计丢包,不需要回显。这样每个阶段只测一个方向,归因清晰。

### 为什么两端都要记录

上行丢包只有 **responder** 能看见(它才知道哪些序号没到)。所以每一方评估自己**收到**的那个方向,再把结果汇总到 prober 统一打印。

### 关键简化:回传结果而非轨迹

30s × 200pps ≈ 6000 样本 ≈ 30KB,若回传原始轨迹需分片重传。改为:**评估器编译进两端,接收方本地评估,只回传约百字节的三档结果**。评估逻辑仍只有一份源码,无重复实现。

### 阶段编排

顺序执行,**不双向并发**——并发会让两个方向的流量互相干扰,污染归因。

| 阶段 | 方向 | 拓扑 | 轨迹记录方 | 时长 |
|---|---|---|---|---|
| S1 | client → server | 单端口 | responder | `--test-duration` |
| S2 | server → client | 单端口 | prober | `--test-duration` |
| S3 | client → server | N 端口轮询 | responder | `--test-duration` |
| S4 | server → client | N 端口轮询 | prober | `--test-duration` |
| R1..R3 | client → server | 单端口 | responder | 各 10s |

- **执行顺序:R1..R3 先跑,然后 S1..S4。** 速率扫描先行的理由是:若它判定为限速/拥塞型丢包,则整份 FEC 推荐的前提已不成立,应尽早把这个警告打给用户,而不是让人等两分钟才看到"FEC 不适用"。判定为限速型时仍继续跑完 S1..S4(数据本身有参考价值),但报告开头即置警告。
- S3/S4 仅在给了 `--data-port-range` 时执行。
- R1..R3 是速率扫描(§7),速率为 `0.5× / 1× / 2×` 的 `--test-pps`,各 10s。三档均为独立探测,不复用 S1 的样本(S1 速率虽同为 `1×`,但复用会把两个阶段的状态耦合在一起,得不偿失)。
- 总时长 ≈ `4 × --test-duration + 30s` ≈ 2.5 分钟(默认值)。**必须打印阶段进度**。

## 4. 探测协议

### 包格式

```c
struct test_hdr_t {
    uint8_t  version;      // 1
    uint8_t  msg_type;     // 见下表
    uint8_t  phase;        // 阶段编号
    uint8_t  reserved;     // 0,接收方校验必须为 0
    uint32_t seq;          // 本阶段内序号,从 0 递增
    uint64_t send_ts_us;   // 发送方时间戳(仅用于 RTT 参考)
};  // 16 bytes
// + padding 到 --test-pkt-size
// + 8 字节 siphash MAC(覆盖前面全部字节,密钥 = key_string)
```

### 刻意不复用 `ctrl_encode` / `ctrl_decode`

那套带 1024 槽 nonce 重放环与 ±60s 时间戳窗口。6000 个探测包会瞬间冲垮 nonce 环,导致**合法探测包被自己的重放保护丢掉**,直接污染丢包测量。因此只复用底层 `siphash24()` 原语,自带干净的头。

### 探测包不做重放保护

重放一个探测包最坏只是让接收方重复计一次(按 seq 落位、重复忽略),已被限速与源锁定覆盖;而引入重放窗口反而会误判丢包。这是有意取舍。

### 消息类型与流程

| msg_type | 方向 | 用途 |
|---|---|---|
| `TEST_HELLO` | prober → responder | 会话建立,携带版本、时长、pps、包长、阶段计划、端口表 |
| `TEST_HELLO_ACK` | responder → prober | 接受;或携带拒绝码与原因 |
| `TEST_PHASE_BEGIN` | prober → responder | 宣告下一阶段(编号、方向、拓扑、预期包数) |
| `TEST_PHASE_ACK` | responder → prober | 确认已就绪 |
| `TEST_PROBE` | 双向 | 探测包本体 |
| `TEST_PHASE_END` | 发送方 → 接收方 | 标记阶段结束,**连发 3 次**(它自己也可能丢) |
| `TEST_REQUEST_RESULT` | prober → responder | 索取结果(用于 RESULT 丢失后重试) |
| `TEST_RESULT` | responder → prober | 回传该阶段三档结果(约百字节) |
| `TEST_BYE` | prober → responder | 结束会话,释放状态 |

```
prober                              responder
  |-- HELLO(params) --------------->|
  |<-- HELLO_ACK -------------------|
  |-- PHASE_BEGIN(S1,up,single) --->|
  |<-- PHASE_ACK -------------------|
  |== PROBE seq=0..N -------------->|   responder 记录轨迹
  |-- PHASE_END(S1) x3 ------------>|
  |<-- RESULT(S1, 三档表) ----------|   responder 本地评估
  |-- PHASE_BEGIN(S2,down,single) ->|
  |<-- PHASE_ACK -------------------|
  |<== PROBE seq=0..N --------------|   prober 记录轨迹并本地评估
  |<-- PHASE_END(S2) x3 ------------|
  ... S3 / S4 / R1..R3 同理 ...
  |-- BYE ------------------------->|
```

`HELLO` 按退避重试,超时则明确报错退出(报错文案见 §8)。

### 发包节奏必须尽量均匀

若发送端自身是突发式的(例如每 5ms 攒一批打出),会**自造时间相关丢包**,把突发测量彻底污染。实现要求:**1ms tick 定时器 + 小数累加(令牌桶式)**,`--test-pps 200` 即精确每 5 tick 发 1 个。

多端口阶段(S3/S4)按端口轮询发送,轮询不改变节奏。

## 5. 轨迹格式

接收侧内存结构:

```c
struct trace_t {
    uint32_t              expected_n;      // 由 PHASE_BEGIN 告知,受上限约束
    uint32_t              pps;             // 发送速率,用于重建发送时刻
    std::vector<uint8_t>  arrived;         // 每个 seq 一字节:0=未到,1=已到
    std::vector<uint32_t> recv_ts_rel_us;  // 相对首个到达包的微秒;未到则 0
};
```

规则:

- **乱序不算丢包**:按 seq 落位,不看到达顺序。
- **重复包忽略第二次**。
- **宽限期**:`PHASE_END` 后等 `max(500ms, 2×RTT)` 再定稿,避免把在途包误判为丢失。
- **兜底超时**:若 `PHASE_END` 三次全丢,接收方在超过 `max(2s, 5/pps)` 没收到新包时自行定稿,不挂死。

### 丢失包的时间如何取得

丢失包的 `send_ts_us` 永远不会到达。但发送节奏均匀且已知,故 seq `k` 的发送时刻重建为 `t0 + k/pps`。**突发时长因此在发送时间轴上精确计算,不受接收侧抖动干扰。** 包内携带的 `send_ts_us` 只用于 RTT 参考。

**不依赖时钟同步**:两端时钟偏差不影响任何结论。

## 6. 评估器算法

评估器是**纯函数**:`evaluate(trace, app_mbps) -> report`。禁用随机数与当前时间,保证同一轨迹的输出完全一致。

### 6.1 统计量

- 丢包率 `p = (N - A) / N`
- **丢包连长分布**:连续丢失的 seq 构成一个 run;统计 run 长度的 p50 / p95 / max
- **突发时长**:长度为 `L` 的 run 在发送时间轴上跨越 `L / pps` 秒;取 p95 作为 `D`
- **采样分辨率** = `1 / N`

### 6.2 候选空间

```
x ∈ [1, 30]
y ∈ [0, min(3x, 254 - x)]
```

约 1500 个候选,穷举成本可忽略。`x` 上限取 30:`x` 越大带宽效率越高,但攒包延迟与被单次突发击穿的风险同步上升。`y` 上限取 `3x`(冗余 300%)——超出后 FEC 已无意义。

### 6.3 残余丢包(核心)

Reed-Solomon 是 MDS 码:一组 `x+y` 个分片中到齐**任意 `x` 个**即可完整还原;少于 `x` 个则**整组全废**(mode 0 的 blob 语义)。因此:

> 组失败 ⟺ 组内丢失数 `> y`
> 每组承载 `x` 个数据包,失败即全丢 ⟹ **残余丢包率 = 失败组的比例**

评估退化为一次滑窗计数:

```
residual(x, y) = 满足「窗口内丢失数 > y」的滑窗占比
                 窗口大小 = x + y,步长 = 1
```

**用步长 1 的滑窗**而非不重叠切块:后者只有 `N/(x+y)` 个样本,大组时噪声很大;滑窗把样本数拉回接近 `N`。代价是窗口重叠、样本不独立,真实置信区间比朴素估计更宽——**报告中必须注明此点**。

### 6.4 `-i` 推导

- 若 p95 连长 `== 1`(丢包基本孤立)→ 建议 `-i 0`。打散买不到任何东西,只会白加延迟。
- 否则:一组 `x+y` 个包摊到 `i` ms,相邻成员间隔 `i/(x+y)` ms。要让一次时长 `D` 的突发最多打中 `y` 个成员:

  ```
  i ≥ D × (x + y) / y        (D = p95 突发时长)
  ```

- `i` 上限 **50ms**(`i` 会给组内后发的包增加最多 `i` ms 延迟);超限则宁可加 `y`。

### 6.5 `-i` 刻意不折进残余丢包

残余丢包一列**只用 `i=0` 的滑窗回放**得出(纯实测,零模型)。`-i` 作为独立一列给出。

理由:打散会改变发包时刻,而轨迹是在未打散节奏下采集的,把 `-i` 折进去就变成叠加模型,可信度下降。

**后果是推荐偏保守**:实际按建议加上 `-i` 后,真实残余丢包应**优于**表中数值。报告中必须写明。

### 6.6 三档选取

| 档 | 目标残余丢包 | 选取规则 |
|---|---|---|
| 省流 | ≤ 1% | 满足目标且 `y/x` 最小 |
| **均衡**(默认推荐) | ≤ 0.1% | 同上 |
| 激进 | ≤ 0.01% | 同上;若目标低于采样分辨率则标注"外推" |

同档并列时,依次取 `i` 更小、`x` 更大(带宽更省)。

**某档无解**时(如丢包 40% 且突发极长),直说"该目标不可达"并给出可达的最好结果,不硬凑数字。

## 7. 速率敏感性与带宽换算

### 7.1 速率扫描

目的只是回答"丢包是否随速率上升"这一个粗判断,故用短程探测:

- 3 档速率:`0.5× / 1× / 2×` 的 `--test-pps`,**每档 10s**
- **只在单端口、上行**做(上行最易被 ISP 限速),不做 4 阶段 × 3 速率的组合爆炸
- 主 FEC 轨迹仍用标称速率跑满 `--test-duration`,与扫描分开

### 7.2 判定规则

设各档丢包率 `p_half / p_nom / p_double`。差异需超过 **3× 二项标准误**(`sqrt(p(1-p)/n)`)才算显著。

| 观测 | 判定 | 工具行为 |
|---|---|---|
| 随速率单调且显著上升 | 限速/拥塞型 | **警告**:FEC 无效甚至有害,加冗余会进一步挤占被限速的管道;建议改用 port-range 分流 |
| 各档在噪声范围内持平 | 随机型 | 正常给出三档推荐 |
| 混杂/不单调 | 不确定 | 如实列出三档原始数字,不下结论 |

### 7.3 带宽换算

`--test-app-mbps R`(缺省取探测速率 `pps × size × 8`)。每档:

```
实际占用 ≈ R × (1 + y/x) × (1 + 逐包头部开销)
```

逐包头部开销:FEC 头 8B + conv 4B + crc32 4B ≈ 16B;1200B 包上约 1.3%。未关 obscure 时还有变长填充,故结果**标注为近似**。

## 9. 错误处理、边界与安全

### 9.1 关键 UX 要求

responder 对 MAC 校验失败**静默丢弃**,因此在 prober 看来「密钥不对」与「防火墙未放通」完全同形。必须两条同时做:

1. responder 侧把 MAC 失败打成 **log_info(限速 1/s)**,让服务端运维一眼可见;
2. prober 的超时报错**必须同时列出两种可能**:"对端无响应:检查 UDP 端口是否放通 / 两端 `-k` 是否一致",不得含糊报"连接失败"。

### 9.2 边界与失败模式

| 情况 | 处理 |
|---|---|
| 未给 `-k` | 参数解析阶段 fatal |
| 版本/参数不符 | `HELLO_ACK` 携带拒绝码与原因,prober 原样打印 |
| `--data-port-range` 仅一端给出或不一致 | `HELLO` 携带端口表,不匹配即明确拒绝 |
| `PHASE_END` 三次全丢 | 接收方兜底超时定稿(§5) |
| `RESULT` 丢失 | prober 重发 `TEST_REQUEST_RESULT`,有限次重试 |
| 样本不足 | `N < 1000` 拒绝"激进"档;`N < 200` 整体拒绝推荐并提示延长时长 |
| 零丢包 | 输出"链路干净" |
| 丢包 > 50% | 警告 FEC 无法挽救,大概率配置错误或链路故障 |
| 丢包集中于尾部 | 检测"末尾 X% 集中丢失",警告本次采样可能因中途中断而无效 |

### 9.3 安全

一个 `PHASE_BEGIN` 能触发 6000 个包外发(放大约 6000:1),必须堵死:

- **强制 `-k` + 每包 MAC**,校验失败立即丢弃。
- **源地址锁定**:会话建立后只接受与 `HELLO` 同源的控制指令,防止中途被接管去打第三方。
- **单活跃会话**:responder 同一时刻只接受一个会话。
- **按源限速**。
- **内存边界**:轨迹数组按对端声明的 `expected_n` 分配,故 `expected_n ≤ 10^7`,且 `--test-duration` / `--test-pps` / `--test-pkt-size` 在参数解析时各自设上限(见 §2)。否则对端一句话即可让本地申请任意大内存。

## 10. 测试

仓库无单测框架(`CLAUDE.md`:靠跑二进制验证),故按仓库习惯:

### 10.1 `--test-selftest`

把合成轨迹灌进评估器跑断言,打印 pass/fail,以退出码反映结果。用例:

- 独立丢包 `p=5%` → `(20,6)` 的残余接近二项预期(容差内)
- 周期性长度 5 的突发 → 断言推荐 `y ≥ 5` 且 `-i > 0`
- 零丢包 → 输出"干净"
- 全丢 → 输出"目标不可达"
- **确定性**:同一轨迹两次运行输出完全一致

### 10.2 `tests/smoke_test_mode.sh`

回环起 responder + prober,注入已知丢包,断言:

- 报告出的丢包率落在容差带内(`--random-drop` 基于伪随机,逐次有波动,故断言容差带而非精确值)
- 退出码为 0
- 报告包含三档推荐

### 10.3 实现细节:丢包注入

现有 `--random-drop` 在 `my_send` 内、以 `dest.cook` 为门(`misc.cpp:228`),而测试模式**不走** `my_send`/cook 那条路,故对测试模式天然无效。**测试模式必须在自己的发送函数里实现同等的丢包注入并复用 `--random-drop` 开关**,否则 smoke 测试无法注入已知丢包。
